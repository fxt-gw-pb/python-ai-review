MMDetection：配置驱动的检测实验

🎯 目标检测

版本提示：3.0 候选版与当前正式版

本章依据的代码包是 MMDetection 3.0.0rc3，属于较早的 3.0 候选版本。rc 表示 release candidate，不能因为都以 3 开头，就认为它与后续 3.x 配置完全相同。

截至 2026-09-05，官方最新正式发布仍是 MMDetection 3.3.0（2024-01-05 发布），当前应按 3.x 的文档组织新工程。它与 2.x 在训练引擎、数据结构和配置方式上有较大差别；即使从 3.0 候选版迁到 3.3.0，也要逐项核对数据集元信息、训练配置，以及 MMCV、MMEngine、PyTorch 的兼容要求。下面的源码解释保留课内版本的行为，迁移时以目标版本文档为准。官方发布记录 · 官方迁移文档

用配置把一个完整实验连接起来

MMDetection 将模型、数据管线、训练循环与评估器拆成组件，再通过配置组装。这样切换检测器时不需要重新写一套训练循环，但也要求理解字段分别由哪个组件读取。配置能成功解析，不意味着实验语义正确；类别表、坐标格式和评估标注仍需人工确认。

本章按 3.0.0rc3 的资料快照理解实现，其训练入口采用 MMEngine Runner。历史代码中的字段、组件名称与依赖关系应成套使用，尤其不要把其他版本示例中的数据元信息字段直接混进来。

一份配置由哪些部分组成

基础配置通常拆成模型、数据集、训练策略和运行时四部分。_base_ 负责继承，子配置按需覆盖字段。模型描述骨干、neck、检测头与训练匹配规则；dataloader 描述采样方式与数据集；pipeline 负责读图、读标注与变换；evaluator 负责将结果与真实标注比较；Runner 组织训练、验证、日志和检查点。

嵌套字典通常按字段合并，而不是简单整块替换。若把 backbone 类型从一种结构换成另一种，却保留不适用的旧字段，可能在构建阶段报错；需要完整替换时可使用配置机制中的 _delete_=True。列表结构则要查看合并语义，不能假定改一个元素就会自动修改所有检测头。

从 Faster R-CNN 看清两阶段检测

ResNet-50 输出多个阶段的特征，FPN 把不同阶段统一为 256 通道。RPN 在金字塔位置生成 anchor，判断前景并回归候选框。第一阶段输出候选区域，第二阶段通过 RoIAlign 从相应特征层抽取固定大小的区域特征，再分类并回归。

课内配置的 RoIAlign 输出 7×7，通道为256，所以每个区域得到 [256,7,7] 特征，随后进入两个全连接层。RPN 的分类主要判断前景/背景；RoI 头才区分多个目标类别。这解释了为什么自定义六类任务通常修改 RoI bbox head 的 num_classes，而不是把 RPN 的前景类别数直接改为6。

RPN 与 RoI 阶段有各自的样本分配规则。RPN 可以用较高 IoU 定义正样本并保留忽略区间；RoI 阶段再从候选中采样并监督。提议框 NMS 与最终检测 NMS 也属于不同环节。调整参数前应先定位它位于哪一阶段。

自定义六类缺陷数据配置

先把数据转换为 COCO 格式，并准备训练与验证图片目录。下面是与本章历史快照对应的教学配置，假定保存在 configs/custom/neu.py：

Python
_base_ = '../faster_rcnn/faster-rcnn_r50_fpn_1x_coco.py'

classes = ('crazing', 'inclusion', 'patches',
           'pitted_surface', 'rolled-in_scale', 'scratches')
data_root = 'data/neu_coco/'

model = dict(roi_head=dict(bbox_head=dict(num_classes=6)))

train_dataloader = dict(
    batch_size=2,
    dataset=dict(
        data_root=data_root,
        metainfo=dict(CLASSES=classes),
        ann_file='annotations/train.json',
        data_prefix=dict(img='train/images/')))

val_dataloader = dict(
    dataset=dict(
        data_root=data_root,
        metainfo=dict(CLASSES=classes),
        ann_file='annotations/val.json',
        data_prefix=dict(img='val/images/')))
test_dataloader = val_dataloader

val_evaluator = dict(ann_file=data_root + 'annotations/val.json')
test_evaluator = val_evaluator

optim_wrapper = dict(optimizer=dict(lr=0.0025))

第一行继承完整可运行结构，因此不用重复写出所有层。模型覆盖只改变最终检测类别数；数据部分同时改变根目录、图片子目录和标注文件。验证 dataloader 与 evaluator 都必须指向同一验证集，否则模型可能在自定义图片上预测，却仍与原 COCO 标注比较。

这份快照读取大写 CLASSES。数据集根据 COCO 的 category ID 建立 cat2label，再转换为连续训练索引。其返回的类别 ID 顺序不一定按传入名称元组重新排序，应检查 cat_ids、cat2label 与显示名称是否对应，而不是只验证类别数相等。

学习率0.0025是按总 batch 从基线16缩到2所给出的线性缩放起点，仍需观察训练稳定性。梯度累积、多卡数量和冻结策略都会改变有效训练条件，不能只看单卡 batch_size 判断学习率是否合适。

数据预处理为什么不全在 pipeline 中

典型 pipeline 先加载图片与标注，执行保持比例的 Resize、RandomFlip，再用 PackDetInputs 组织输入。模型内部的 DetDataPreprocessor 负责归一化、通道转换与批量 padding。因此，如果在自定义 pipeline 中再次除以255或重复减均值，可能与模型预处理叠加，造成输入分布错误。

课内 Faster R-CNN 使用按0到255像素尺度定义的 mean、std，并设置 BGR→RGB。它与一些独立 PyTorch 脚本“先除以255，再用0到1均值归一化”的数学含义可以对应，但不能把两套数值直接交叉使用。

多尺度图片在 batch 中可能补到共同尺寸，框与图像元信息要保留原始尺寸、缩放比例和有效图像范围。评估器依赖这些信息恢复坐标，因此不要在自定义打包函数中只保留图像张量，丢掉 data_samples。

Runner 怎样启动训练

训练入口解析参数，注册模块，读取配置并合并命令行覆盖，然后确定工作目录、混合精度和恢复选项，最后构建 Runner 并调用 train()。下面的命令是准备好配置和数据后的运行示例：

Shell
python tools/train.py configs/custom/neu.py --work-dir work_dirs/neu

启动前先打印合并后的配置，确认模型头为6类、训练与验证标注正确、学习率和训练轮数符合预期。1x 计划在这份快照中是12轮，包含前500次迭代的线性热身，以及第8、11轮附近的学习率衰减。不能把“1x”理解成只训练1轮。

从预训练权重初始化与恢复完整训练状态不同。前者使用已有参数开始新实验；后者还应恢复优化器、学习率计划和训练进度。换了数据或类别后，不宜不加检查地恢复旧实验状态。

用最小实验验证整条链路

先抽取少量训练图，画出 pipeline 处理后的框；再确认一次前向和反向能得到有限损失。关闭强增强，对小样本反复训练，检查模型能否记住这些样本。通过后，再使用完整训练集与固定验证集。

每次实验至少保存最终合并配置、环境版本、数据划分清单、随机种子、训练日志、最佳权重以及一组失败图片。验证集用于选择模型与阈值，测试集用于最终报告。不要反复根据测试结果调整参数，否则测试集已经参与了模型选择。

训练损失正常但 AP 为0时，先排查类别映射、图像ID、坐标还原和评估文件；只有训练 AP 高、验证 AP 低时，再重点考虑过拟合与数据分布差异。一个可靠实验的价值，不仅是得到分数，还要能解释失败发生在哪一环。

练习：只有一处路径没改

你已把训练和验证 dataloader 改成自己的六类数据，但 val_evaluator.ann_file 仍指向原 COCO。可能出现什么问题？model.roi_head.bbox_head.num_classes=6 是否包含背景类？

✅ 参考答案

评估器可能找不到对应图片ID、类别或正确真实框，导致报错或无意义的低分。预测与评估标注必须属于同一数据划分。这里的 num_classes=6 指目标类别数，背景由检测头内部的分类实现处理，通常不需要手工写成7。
