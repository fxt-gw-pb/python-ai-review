人脸关键点与眨眼计数：从坐标到时间状态

🖼️ OpenCV 图像处理

人脸检测与关键点定位

人脸检测先给出脸所在的矩形，关键点模型再在这个区域中预测眼睛、鼻子、嘴和下颌等坐标。关键点不是分类标签，也不是图像分割掩模。项目使用 dlib 的人脸检测器和 68 点形状预测模型，再把返回对象转成 (68,2) 的 NumPy 数组，以便索引、绘图和计算距离。

Python
import numpy as np

def shape_to_array(shape):
    points = np.zeros((shape.num_parts, 2), dtype=np.int32)
    for index in range(shape.num_parts):
        points[index] = (shape.part(index).x, shape.part(index).y)
    return points

这段保留原 shape_to_np 的核心。每行是 (x,y)，不是 (row,column)；只有真正访问图像数组时才改成 [y,x]。人脸检测器中的上采样参数会影响小人脸检出和速度，但不会改变模型输出“68 个语义位置”的定义。

68 个点如何分区

项目用半开切片区间：下颌 0:17、右眉 17:22、左眉 22:27、鼻子 27:36、右眼 36:42、左眼 42:48、嘴 48:68。注意每个终点不包含在内，所以每只眼恰好六个点。左右名称按模型标注约定理解，不能简单等同于观看者屏幕上的左右。

可视化时，下颌是开放曲线，依次连线；眼睛、眉毛等区域则计算凸包并填色，再与原图加权叠加。凸包是包住点集的最小凸多边形，不等于精确器官边界。例如嘴唇实际有内外轮廓，凸包会把内部空洞也包在里面。

裁剪器官 ROI 使用关键点的外接矩形。若要在裁剪图上重新画关键点，需将原坐标减去 ROI 左上角，再乘缩放比例；原项目在完整图上画点、另外展示裁剪图，所以不需要这一步。选择坐标系应始终明确。

源码还声明了一个五点索引字典，但实际可视化循环使用的是 68 点版本。不能只替换模型文件就假设剩余代码兼容五点输出，切片范围、眼部点数和后续 EAR 都必须与模型定义一致。

EAR：用比例减少尺度影响

设一只眼的六点沿轮廓排列为 $p_0,\ldots,p_5$，眼睛纵横比定义为

$$ \operatorname{EAR}=\frac{\|p_1-p_5\|_2+\|p_2-p_4\|_2}{2\|p_0-p_3\|_2}. $$

分子是两条近竖直眼裂高度，分母是两倍近水平眼宽。闭眼时两条高度通常变小，宽度变化相对较少，因此 EAR 降低。若所有坐标按同一比例缩放，分子分母同时变化，比例保持不变；但头部旋转、透视、遮挡和关键点误差并不会被这个比值全部消除。

Python
import numpy as np

def eye_aspect_ratio(eye):
    eye = np.asarray(eye, dtype=np.float32)
    if eye.shape != (6, 2):
        raise ValueError('每只眼需要 6 个二维关键点')
    vertical = np.linalg.norm(eye[1]-eye[5]) + np.linalg.norm(eye[2]-eye[4])
    horizontal = np.linalg.norm(eye[0]-eye[3])
    if horizontal <= 1e-6:
        return None
    return float(vertical / (2.0 * horizontal))

这是原函数的教学改写，增加形状与分母检查。原项目分别计算左右眼，再取平均；若一侧眼睛被遮挡，平均值也可能被拉低，因此需要判断关键点质量，不能把所有低值都解释为闭眼。

一次眨眼不是连续闭眼帧数

项目阈值为 0.3，连续帧数阈值为 3。低于阈值时累计计数；重新睁眼时，如果此前已连续至少三帧低于阈值，眨眼总数才加一，然后清零。这个状态机防止同一次闭眼在连续五帧中被算成五次眨眼。

Python
closed_frames = 0
blink_count = 0
for ear in ear_sequence:
    if ear is None:
        closed_frames = 0
        continue
    if ear < 0.3:
        closed_frames += 1
    else:
        if closed_frames >= 3:
            blink_count += 1
        closed_frames = 0

这是从原循环提取的可读状态逻辑，ear_sequence 是按时间排列的单个人 EAR。它在睁眼时确认事件，因此视频恰好结束于闭眼期间时，不会自动确认最后一次眨眼。这是事件定义，而不只是程序遗漏；需要根据任务决定如何处理未结束片段。

为什么要考虑帧率与身份

三帧在 30 FPS 下约为 0.1 秒，在 10 FPS 下约为 0.3 秒，同样的帧数并不代表同样的持续时间。处理帧率不稳定时，可使用时间戳累积闭眼时长。人脸暂时未检出也不等于眼睛闭合，应设为观测缺失，而不是继续累加。

原代码对所有检测到的人脸共用全局 COUNTER 与 TOTAL，多个人会相互影响计数。扩展为多人时，需要先建立稳定的人脸或目标身份，再按每个人分别维护状态；仅凭当前帧里脸框的列表顺序无法保证身份连续。

疲劳案例实际完成了什么

压缩包名称使用“疲劳检测”，实际代码输出 EAR 和眨眼次数，没有建立完整疲劳判定规则或验证过程。学习成果应描述为“眼部关键点与眨眼计数原型”。若要研究疲劳相关行为，需要明确持续闭眼、时间窗口等可观测指标，建立标注与评估，不能直接把一次低 EAR 或较多眨眼当成确定结论。

练习

  1. 两条竖直距离均为 6，水平距离为 24，EAR 是多少？
  2. 序列 [0.35,0.2,0.2,0.2,0.2,0.35] 会记几次眨眼？
  3. 为什么把六点坐标整体放大两倍不会改变 EAR？
  4. 多人画面中为何不能只用一个连续帧计数器？
✅ 参考答案
  1. $(6+6)/(2\times24)=0.25$。
  2. 一次。四帧低值属于一次连续闭眼，在最后恢复高值时确认事件。
  3. 所有欧氏距离都放大两倍，比值中相互约去；这只对统一尺度变化成立。
  4. 不同人的观测会交替修改同一状态，A 的闭眼可能与 B 的睁眼拼成错误事件，需要每个身份独立维护计数和时间。
